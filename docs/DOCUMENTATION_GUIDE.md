# Documentation Guide

MockSyn is a framework. Features must be documented before implementation.

## Documentation Types

| Type | Purpose |
| --- | --- |
| Markdown docs | Explain a feature, when to use it, how it works, and examples. |
| Doc strings | Document public API symbols for Xcode and DocC. |
| Inline comments | Explain non-obvious implementation logic. |

## Markdown Feature Docs

Each user-facing feature gets a Markdown page before implementation. The page must include:

- what the feature does;
- when to use it;
- when not to use it;
- setup requirements;
- basic example;
- advanced example when relevant;
- expected failure behavior;
- limitations;
- compatibility notes for Swift 5.9 and Swift 6.

Recommended layout:

```text
docs/features/<feature-name>.md
```

## Doc Strings

Every public API must have a doc string.

Good:

```swift
/// Verifies that the selected invocation matched the expected call count.
///
/// Use this after exercising the system under test.
public func called(_ count: CallCount)
```

Avoid documenting implementation details in public doc strings.

## Inline Comments

Inline comments are only for internal logic that is not obvious from code shape.

Good:

```swift
// Keep the lock scope narrow so matcher closures execute outside the critical section.
```

Bad:

```swift
// Increment the count by one.
```

## Generated Code Comments

Generated code should be readable but not noisy. Generated declarations may include a short header:

```swift
// Generated by MockSyn. Do not edit the macro expansion.
```

Generated members should not include verbose comments.

## Documentation Review Rule

No feature is implementation-ready until:

- its Markdown feature page exists;
- public API doc strings are specified;
- diagnostics and failure behavior are documented;
- examples compile in the intended support matrix.
